## Scope and behavior

Mega Board only. The authenticated hub shows a persistent card for each eligible live account-owned Mega Board match, including paused matches. It uses the existing app notification styling next to admin feedback notices and the existing browser saved-session recovery credentials. Return refreshes the account query and then uses the ordinary `game:reconnect` handler with additional mandatory account/match checks and `force: false`. A connected seat on another device is refused. A missing local recovery session is explained; **account-only cross-device reclaim is not implemented**. A saved session for a different room is never used to join that room.

The card remains while browsing hub sections; it is not overlaid on another game's screen. Leaving Mega Board for the hub and reopening the app at the hub makes it available again. Existing `/game/CODE` reload recovery remains the existing token-authorized route. This batch does not add other game adapters. Paused matches say that moves/timers are frozen; returning does not resume them. Eligibility respects the existing host-disconnect deadline (including the existing longer paused-match grace); no new expiry policy is invented.

Foreground polling is every 10 seconds while visible, with focus, online and visibility refresh. Hidden transitions abort in-flight polling; component unmount/account-key change cancels old responses. Failed queries clear cards rather than displaying stale ownership. Finished/won, forfeited, bankrupt, expired, missing and mismatched room/state identities are excluded on each fetch and on return. Logout/account switch unmounts the account-keyed card; an in-flight socket acknowledgement cannot apply a recovered game after the current account changes. Browser recovery credentials remain in the existing saved-session UI; this feature does not publish them or treat their presence as account ownership.

Only the latest explicitly public purchase-complete, trade-complete, bankruptcy or rent-payment summary is projected. No pending trade/card or private state is serialized. The card shows context, not a historical toast queue, and equal query snapshots do not rerender. Existing GameBoard first-mount notice cursor still seeds all retained notices without replaying them on reconnect. No automatic focus, modal, sound or OS permission request is added by the card.

## Security boundary

`GET /accounts/active-matches` uses the existing `getAuthenticatedAccount` session verification, returns 401 when unauthenticated/revoked and uses `Cache-Control: no-store`. The existing service worker already bypasses `/accounts/` requests. Discovery uses only persisted server-side `RoomPlayer.replayAccountId`; names, room-code knowledge and payload-supplied ownership never authorize discovery.

Response allowlist: `gameId`, `code`, stable `matchId` (`mega-CODE-gameStartedAt`, matching the ordinary Mega replay identity), `paused`, and nullable notice `{id,title,message}`. It contains no account IDs, socket/seat IDs, recovery keys, private hands, decks or pending decisions.

The notice's reconnect request adds `activeAccountId` and `activeMatchId`. The handler verifies the socket request's still-valid account session, exact persisted token-selected seat ownership, matching live state identity and eligibility before any mutation. Force is refused on this path; the existing reconnect utility additionally refuses a connected seat owned by another socket. No spectator seat is created. Guest/manual ordinary reconnect retains its token checks and does not acquire account ownership. Inspection of `reconnectRoomPlayer`, `toPublicGameRoom`, persisted player handling and initial game-player construction found no existing replayAccountId reassignment or public serialization through these paths. Ordinary recovery tokens remain bearer credentials as documented in SECURITY.md; this is not a claim that every legacy reconnect is account-bound.

Existing saved-session Resume previously passed force=true. It now uses false. The separate manual Mega Board control is explicitly labelled **Take Over Session** and uses the existing in-app HGR **ConfirmDialog**, not a native browser prompt. After validating the manual fields, it snapshots the room, player name, recovery token and current account (including guest identity). Cancel/Escape discard the snapshot; account switch/logout reset it. Only explicit confirmation consumes the snapshot once and invokes existing force:true recovery, with a warning that another browser will be disconnected. The recovery token is not displayed in the dialog. Other games' recovery controls are unchanged; the return notice remains force:false.

## PWA background phase — unfinished

Existing `pushNotifications.ts` consent/topics cover **invites** and **messages**, not game decisions. Existing service-worker `push` and `notificationclick` support does not establish consent or secure match-topic subscriptions. No decision push, background monitoring, automatic notification enablement or closed-PWA delivery is implemented. A separate phase requires explicit game-alert preferences, recipient/seat scoping and revocation, match lifecycle handling, deduplication and real installed-device delivery acceptance.
